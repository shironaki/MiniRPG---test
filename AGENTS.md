## 1. Жёсткие запреты / HARD RULES — нарушение = отклонение работы

> **Обновление (этап 15, по решению владельца):** активная разработка
> переехала в **`/v3`** — новая игра «Пепел и Зерно» (survival-песочница,
> колония, сюжет; см. `docs/V3-CONCEPT.md` и `v3/README.md`). `/v2` отныне
> считается завершённой версией и правится только по отдельной просьбе
> владельца. Всё, что ниже сказано про «работаем в `/v2`», читается как
> «работаем в `/v3`»; запреты на основу v1, лицензию и зависимости
> действуют без изменений.

### Главное правило: **ОСНОВУ НЕ ТРОГАЕМ, РАБОТАЕМ В `/v2`**

«Основа» — это готовая игра **v1** в корне репозитория и лицензия:

```
index.html   style.css   js/**   assets/**   LICENSE
```

Она доработана и считается законченной. Вся новая разработка ведётся
**только внутри папки `/v2`** (плюс `docs/` для записей). Если кажется, что
задачу нельзя решить без правки v1 — это повод спросить владельца, а не
править.

| # | Правило | Rule (EN) |
|---|---------|-----------|
| 1 | **Не менять основу:** `index.html`, `style.css`, `js/**`, `assets/**`. Готовая игра v1 остаётся как есть. | Never touch the finished v1 game at the repo root. |
| 2 | **Не менять `LICENSE` и строку копирайта** `Copyright (c) 2026 shironaki`, а также поля `license`/`author` в `package.json`. | Never modify the licence, the copyright line or those package.json fields. |
| 3 | Ветка **`main` — стабильная основа-релиз**. Напрямую в неё не пушить; изменения попадают туда только через PR, который вливает владелец. | `main` is the stable release branch: no direct pushes, owner merges PRs. |
| 4 | **Никогда не использовать `git push --force`** и не переписывать чужую историю. | Never force-push, never rewrite existing history. |
| 5 | Не удалять и не переименовывать `.git`, `LICENSE`, `AGENTS.md`, `CONTRIBUTING.md`, `.github/`. | Do not delete or rename these paths. |
| 6 | Не добавлять зависимости и сборщики. Проект **принципиально без `node_modules`**, чистый ES5/ES6 в браузере. | No dependencies, no bundlers, no build step. Ever. |
| 7 | Не коммитить бинарные артефакты, скриншоты-черновики, дампы, `node_modules`. | No generated artifacts in Git. |

Пункты 1, 2 и 6 проверяются автоматически: `.github/workflows/guard.yml`
роняет пулл-реквест при попытке изменить основу, лицензию или добавить
зависимости. `.github/CODEOWNERS` зовёт владельца в ревью.

Отдельно: `v2/js/main.js` — оркестратор всей 2D-версии. Менять его **можно**
(без него не сделать новых систем), но осторожно и осознанно: CI пометит такой
PR предупреждением, чтобы владелец посмотрел внимательнее.

## 2. Ветки / branching

Работа ведётся **только в новой ветке**, никогда прямо в `main`.

```bash
# 1) взять актуальное состояние
git fetch origin
git checkout -b work/<короткое-имя-задачи> origin/main

# 2) работать в /v2, коммитить атомарно, пушить только свою ветку
git push -u origin work/<короткое-имя-задачи>

# 3) открыть Pull Request — вливает владелец
gh pr create --base main --head work/<...>
```

* **`main`** — стабильная основа: доработанная игра v1 + текущее состояние v2
  + документация. Прямых пушей в неё нет, только PR.
* Имя новой ветки: `work/<задача>`, `feat/<фича>`, `fix/<баг>`.
* Одна ветка = одна логическая задача. Ветку не переиспользовать после мержа.
* Историческая рабочая ветка — `arena/01a0eee6-minirpg-test` (с неё
  публикуется GitHub Pages). Если владелец просит работать от неё —
  подставь её вместо `main` в командах выше.

## 3. Рабочий протокол (его придерживались все предыдущие итерации)

```
SCAN → AUDIT → FIX → VERIFY → EXTEND → COMMIT → LOG
```

1. **SCAN** — прочитать `docs/HANDOVER.md` и `docs/ARCHITECTURE.md`, осмотреть
   затрагиваемые файлы целиком, а не по кускам.
2. **AUDIT** — найти реальные проблемы/риски до того, как писать код.
3. **FIX** — чинить найденное.
4. **VERIFY** — обязательно, каждый раз:
   ```bash
   npm test                     # должно быть 192/192 passed (см. HANDOVER)
   node --check <каждый изменённый .js>
   npm run serve                # http://localhost:8080 и /v2/ должны открываться
   ```
   Ни один коммит не должен ронять тесты. Упало — чини, а не отключай тест.
5. **EXTEND** — только после того, как всё зелёное, добавлять новое.
6. **COMMIT** — атомарно: один коммит = одно осмысленное изменение, с внятным
   сообщением (что и **зачем**, а не «fixes»).
7. **LOG** — обновить `docs/CHANGELOG.md` и, если менялась архитектура,
   `docs/ARCHITECTURE.md`. Отчитаться владельцу: что сделано, что проверено,
   что сломалось и почему.

**Честность важнее красивого отчёта.** Если что-то не проверено — так и писать.
Не выдавать непроверенное за работающее.

## 4. Технические правила кода

* Vanilla JS, без зависимостей. Скрипты подключаются по порядку в `index.html`
  (v1) и `v2/index.html` (v2). **Добавил файл — добавь `<script>` в index.html
  И в тестовый харнесс** (`tests/harness.js` / `v2/tests/harness.js`, списки
  `FILES` и `EXPORTED`), иначе тесты/игра упадут с `X is not defined`.
* Каждый модуль заканчивается совместимым экспортом:
  ```js
  if (typeof module !== "undefined" && module.exports) module.exports = { Thing };
  ```
* v2 не дублирует логику v1: боевая система, предметы, квесты берутся из `js/*`
  через `../js/*.js`. Не форкать логику — переиспользовать.
* Логика должна быть **чистой и тестируемой**: состояние и правила отдельно,
  рисование отдельно (`v2/js/render/*`). Рандом — через инъекцию `rng`.
* Новая игровая система = новые юнит-тесты в `v2/tests/engine.test.js`.
* UI-тексты игры — на русском (как уже есть). Комментарии в коде — английский.
* Никаких `innerHTML` с пользовательскими данными без экранирования
  (в проекте уже был security-проход, не откатывать его).

## 5. Что нельзя ломать (проверено и принято владельцем)

* Пиксель-арт героя и мобов — **принят**, стиль менять нельзя без согласования.
  Ранее отклонены: статичный «прыгающий» спрайт, спрайт-лист, капсульный риг.
* Герой — **маленький, чиби** (`H = h * 1.7`). Не увеличивать.
* **В деревне нет мобов** — враги только в лесу/пещере.
* Здания в деревне все разные и соответствуют своей функции.
* День/ночь, живые NPC, сбор ресурсов, ферма — работающие системы, см. HANDOVER.
