## 2. Ветки / branching

Работа ведётся **только в новой ветке от текущей рабочей ветки проекта**.

```bash
# 1) взять актуальное состояние работы
git fetch origin
git checkout -b work/<короткое-имя-задачи> origin/arena/01a0eee6-minirpg-test

# 2) работать, коммитить атомарно, пушить только свою ветку
git push -u origin work/<короткое-имя-задачи>

# 3) открыть Pull Request В СВОЮ РАБОЧУЮ ВЕТКУ-БАЗУ (НЕ в main)
gh pr create --base arena/01a0eee6-minirpg-test --head work/<...>
```

* Базовая ветка со всей текущей работой: **`arena/01a0eee6-minirpg-test`**
  (38 коммитов, содержит v1 и v2 — см. `docs/HANDOVER.md`).
* Имя новой ветки: `work/<задача>`, `feat/<фича>`, `fix/<баг>`.
* **PR всегда в рабочую ветку, никогда в `main`.** Решение о `main` принимает
  только владелец.
* Одна ветка = одна логическая задача. Ветку не переиспользовать после мержа.

## 3. Рабочий протокол (его придерживались все предыдущие итерации)

```
SCAN → AUDIT → FIX → VERIFY → EXTEND → COMMIT → LOG
```

1. **SCAN** — прочитать `docs/HANDOVER.md` и `docs/ARCHITECTURE.md`, осмотреть
   затрагиваемые файлы целиком, а не по кускам.
2. **AUDIT** — найти реальные проблемы/риски до того, как писать код.
3. **FIX** — чинить найденное.
4. **VERIFY** — обязательно, каждый раз:
   ```bash
   npm test                     # должно быть 192/192 passed (см. HANDOVER)
   node --check <каждый изменённый .js>
   npm run serve                # http://localhost:8080 и /v2/ должны открываться
   ```
   Ни один коммит не должен ронять тесты. Упало — чини, а не отключай тест.
5. **EXTEND** — только после того, как всё зелёное, добавлять новое.
6. **COMMIT** — атомарно: один коммит = одно осмысленное изменение, с внятным
   сообщением (что и **зачем**, а не «fixes»).
7. **LOG** — обновить `docs/CHANGELOG.md` и, если менялась архитектура,
   `docs/ARCHITECTURE.md`. Отчитаться владельцу: что сделано, что проверено,
   что сломалось и почему.

**Честность важнее красивого отчёта.** Если что-то не проверено — так и писать.
Не выдавать непроверенное за работающее.

## 4. Технические правила кода

* Vanilla JS, без зависимостей. Скрипты подключаются по порядку в `index.html`
  (v1) и `v2/index.html` (v2). **Добавил файл — добавь `<script>` в index.html
  И в тестовый харнесс** (`tests/harness.js` / `v2/tests/harness.js`, списки
  `FILES` и `EXPORTED`), иначе тесты/игра упадут с `X is not defined`.
* Каждый модуль заканчивается совместимым экспортом:
  ```js
  if (typeof module !== "undefined" && module.exports) module.exports = { Thing };
  ```
* v2 не дублирует логику v1: боевая система, предметы, квесты берутся из `js/*`
  через `../js/*.js`. Не форкать логику — переиспользовать.
* Логика должна быть **чистой и тестируемой**: состояние и правила отдельно,
  рисование отдельно (`v2/js/render/*`). Рандом — через инъекцию `rng`.
* Новая игровая система = новые юнит-тесты в `v2/tests/engine.test.js`.
* UI-тексты игры — на русском (как уже есть). Комментарии в коде — английский.
* Никаких `innerHTML` с пользовательскими данными без экранирования
  (в проекте уже был security-проход, не откатывать его).

## 5. Что нельзя ломать (проверено и принято владельцем)

* Пиксель-арт героя и мобов — **принят**, стиль менять нельзя без согласования.
  Ранее отклонены: статичный «прыгающий» спрайт, спрайт-лист, капсульный риг.
* Герой — **маленький, чиби** (`H = h * 1.7`). Не увеличивать.
* **В деревне нет мобов** — враги только в лесу/пещере.
* Здания в деревне все разные и соответствуют своей функции.
* День/ночь, живые NPC, сбор ресурсов, ферма — работающие системы, см. HANDOVER.
