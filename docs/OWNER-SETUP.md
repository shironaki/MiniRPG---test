# 🔧 OWNER-SETUP — что делает владелец

Тяжёлая бюрократия не нужна. Договорённость простая:

> **`main` — стабильная основа. Вся новая работа — в папке `/v2`, в отдельных
> ветках, и вливается в `main` через PR, который смотрит владелец.**

Ниже — минимум действий.

---

## 1. Обновить `main` (один раз)

Сейчас в `main` лежит **самая первая сырая загрузка** проекта: только
`index.html`, `js/`, `style.css`. Она отстала на 40 коммитов и не содержит ни
доработанной игры v1 (тесты, безопасность, квесты, карма, союзники), ни v2, ни
документации.

Обновление — это **fast-forward** (рабочая ветка выросла прямо из `main`,
конфликтов быть не может). Вливаем подготовленный PR кнопкой **Merge** —
и `main` становится нормальной основой:

* доработанная игра **v1** в корне — та самая «основа», которую не трогаем;
* текущее состояние **v2** в `/v2/` — точка, с которой продолжается работа;
* документация, тесты, CI.

## 2. Доступ работнику

`Settings` → `Collaborators and teams` → добавить с ролью **Write**.
Этого хватает, чтобы создавать ветки и PR, и не хватает, чтобы что-то снести.

## 3. Хотите — включите защиту ветки (необязательно)

Если позже захочется, чтобы `main` нельзя было испортить даже случайно:
`Settings` → `Branches` → `Add branch ruleset`, паттерн `main`,
галочки **Require a pull request before merging** и **Block force pushes**.
Без этого правила всё тоже работает — просто держится на договорённости.

## 4. GitHub Pages

Сейчас сайт публикуется **с рабочей ветки** `arena/01a0eee6-minirpg-test`
(`https://shironaki.github.io/MiniRPG---test/`, v2 — по адресу `/v2/`).
Два варианта, оба нормальные:

| Вариант | Что даёт |
|---------|----------|
| Оставить как есть | Сайт всегда показывает самое свежее, что вы делаете в рабочей ветке; `main` живёт как архив-основа |
| Переключить на `main` (`Settings` → `Pages` → `Branch: main`) | На сайте только то, что вы сами одобрили и влили; эксперименты не попадают к игрокам |

Рекомендация: переключить на `main` **после** его обновления — тогда публичная
ссылка всегда стабильна, а работника проверяете по его ветке локально.

---

## 5. Как быстро проверять работу

```bash
git fetch origin
git log --oneline origin/main..origin/work/<его-ветка>   # что он сделал
git diff --stat origin/main origin/work/<его-ветка>      # объём и какие файлы
npm test                                                 # 192+ passed
npm run serve                                            # глазами: / и /v2/
```

В самом PR смотреть три вещи: вкладку **Checks** (CI и Guard зелёные),
вкладку **Files changed** (что реально поменяно) и заполненный чек-лист.

Красные флаги при ревью:

* изменения вне `/v2` — то есть кто-то полез в основу;
* тесты «поправлены» вместо кода (ослаблены проверки, тесты закомментированы);
* появились зависимости, lock-файлы, `node_modules`;
* большой PR без описания и без обновления `docs/CHANGELOG.md`;
* новый JS-файл не подключён в `v2/index.html` и в харнесс — игра откроется,
  но упадёт в браузере.

## 6. Что уже проверяется автоматически

`.github/workflows/guard.yml` роняет PR, если:

* тронута основа: `js/**`, `assets/**`, `index.html`, `style.css`, `LICENSE`;
* изменена строка `Copyright (c) 2026 shironaki` или поле `license`;
* появились зависимости или lock-файлы.

Правка `v2/js/main.js` разрешена (без неё не сделать новых систем) — CI просто
пометит такой PR предупреждением, чтобы вы взглянули внимательнее.
`.github/workflows/ci.yml` на каждый push проверяет синтаксис всех скриптов и
прогоняет 192 теста.
