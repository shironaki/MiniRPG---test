# 🔐 OWNER-SETUP — что владельцу сделать руками на GitHub

Файлы в репозитории (`AGENTS.md`, `CODEOWNERS`, `guard.yml`) задают правила и
автоматически роняют неправильные пулл-реквесты. Но **настройки самого
репозитория** (защита веток, права доступа) меняются только владельцем через
веб-интерфейс GitHub — из кода и из агента они недоступны.

Ниже — минимум на 5 минут, который делает заморозку `main` по-настоящему
нерушимой, а не «на честном слове».

---

## 1. Заморозить ветку `main` (главное)

`Settings` → `Branches` → `Add branch ruleset` (или `Add rule` в старом UI).

* **Branch name pattern:** `main`
* Включить:
  * ✅ **Require a pull request before merging** → *Require approvals: 1*
  * ✅ **Require review from Code Owners** (работает вместе с `.github/CODEOWNERS`)
  * ✅ **Require status checks to pass** → выбрать проверки `CI / test`,
    `Guard / Копирайт на месте`, `Guard / Защищённые файлы не тронуты`
  * ✅ **Block force pushes**
  * ✅ **Restrict deletions**
  * ✅ **Do not allow bypassing the above settings** — иначе правило обходится
* Итог: в `main` нельзя запушить напрямую и нельзя влить без вашего ревью.

> Если хочется, чтобы правило не мешало лично вам — оставьте
> «Do not allow bypassing» выключённым; но тогда и любой другой админ сможет
> обойти. Рекомендуется включить.

## 2. Защитить рабочую ветку (по желанию)

То же самое для паттерна `arena/*` — тогда работник тоже не сможет
переписать историю рабочей ветки force-push-ем, а только вливать PR.

## 3. Права работника

`Settings` → `Collaborators and teams` → добавить работника с ролью **Write**.

* **Write** — может создавать ветки и PR, **не может** менять настройки
  репозитория, удалять его и обходить защиту веток. Это то, что нужно.
* **Не давать** роль `Admin` или `Maintain`.

## 4. Проверить, что защита работает

После настройки попросите работника (или проверьте сами со второй учётки):

1. Попытка `git push origin main` → должна быть **отклонена** GitHub-ом.
2. PR с изменением `v2/js/main.js` → проверка **Guard / Защищённые файлы**
   падает красным, мерж заблокирован.
3. PR в `main` → Guard падает с сообщением, что `main` заморожена.
4. Обычный PR в `arena/01a0eee6-minirpg-test` с зелёными тестами → проходит
   и ждёт вашего ревью.

## 5. Как быстро проверять, что наработал работник

```bash
git fetch origin
git log --oneline origin/arena/01a0eee6-minirpg-test   # что появилось нового
git diff origin/arena/01a0eee6-minirpg-test~5 --stat   # объём изменений
npm test                                               # 192+ passed
npm run serve                                          # глазами: / и /v2/
```

Смотреть в PR: вкладку **Files changed** (что реально поменяно), вкладку
**Checks** (CI и Guard зелёные), и заполненный чек-лист из шаблона PR.

Признаки, на которые стоит обратить внимание при ревью:

* тесты «поправлены» вместо кода (ослаблены проверки, `it(...)` закомментированы);
* появились `node_modules`, lock-файлы, зависимости — это запрещено;
* большой PR без описания и без обновления `docs/CHANGELOG.md`;
* правки в защищённых файлах «заодно»;
* новые файлы, не подключённые в `index.html` / харнесс тестов — игра
  откроется, но упадёт в браузере.
